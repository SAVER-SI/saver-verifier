# x402 Payment Integration

SAVER Verifier uses x402 to enable machine-to-machine payments.

## Payment Flow

1. Discover the service and read its request contract.
2. Submit a valid verification request.
3. Read the 402 payment challenge.
4. Authorize payment and retry with an x402 v2 wallet client.
5. Receive the verification result and settlement metadata.

## Network

| Setting | Value |
|---|---|
| Protocol | x402 v2 |
| Network | Base Mainnet |
| Asset | USDC |

## Why x402

x402 enables autonomous systems to pay for services directly without traditional API key billing flows.

This allows AI agents and software systems to:

- discover services automatically

- understand pricing requirements

- authorize payment programmatically

- consume results directly

## Discovery

x402 metadata:

```text
https://api.saververify.com/.well-known/x402
```


## Request and retry

Send `POST https://api.saververify.com/v2/verify` with `Content-Type: application/json`:

```json
{
  "claim": "The Ethereum mainnet launched on July 30, 2015.",
  "context": ""
}
```

Only `claim` and `context` are accepted. Invalid input is rejected before payment with HTTP 400 or 413. Do not send an empty body just to obtain payment requirements.

On HTTP 402, read the base64-encoded JSON in the `PAYMENT-REQUIRED` response header. The body may be `{}`. An x402 v2 wallet client authorizes payment and retries the same POST body with `PAYMENT-SIGNATURE`. A successful paid response includes the result and `PAYMENT-RESPONSE`. Header names are case-insensitive. A 402 response is a challenge or payment rejection, not a receipt.

## Client examples

[verify-agent.mjs](../examples/verify-agent.mjs) is an unpaid discovery demo. It displays the challenge and stops at 402.

[paid-verify.mjs](../examples/paid-verify.mjs) uses `@x402/fetch` and `@x402/evm` to sign and retry. Install repository dependencies before running it. It makes a real Base Mainnet payment when run with a funded wallet and `SAVER_PRIVATE_KEY`; do not run it as an unattended smoke test.

Never commit or share wallet keys. Require explicit approval or enforce per-call, session and daily spending limits. Validate the expected recipient, asset, network and amount before signing. The shared client enforces the exact 0.20-USDC Base payment, recipient and asset, permits only one signed send, and validates the settlement receipt.

## Failure handling

Retain the request ID when troubleshooting. Do not automatically sign another payment after a timeout or lost connection: the previous request may have settled even if its result was not received. Use a saved `SAVER-RECOVERY-TOKEN` with `GET /results` before considering another payment.

An HTTP 200 `insufficient_evidence` result is still a completed verification. Use SAVER as an evidence signal within your own execution and wallet policy.

See the [API contract](api.md) for request constraints and response fields.


## Linked evidence and canonical identity

Prefer `POST https://api.saververify.com/v2/verify` for explicit evidence/source links. The request body and 0.20 USDC payment policy are the same as `/verify`. The original endpoint remains supported.

Use https://saververify.com/agent-tool.json for a flat tool schema. `method`, `type`, `bodyType` and `body` describe discovery transport and must not be submitted as verification fields. Read actual paid response records at https://saververify.com/examples.json before integrating. These purchases are operator-funded tests, not organic usage.

## Paid demonstration provenance

The [public collection](https://saververify.com/examples.json) contains exactly three current operator-funded production responses, each with a successful 0.20 USDC Base transaction. This capture batch spent 0.60 USDC. Records include the service contract version and disclose caller-provided source URLs. These are demonstrations, not organic purchases or an independent accuracy benchmark.

## Correcting a request automatically

Both verification routes reject invalid input before payment. HTTP 400/413 responses preserve `error`, `message` and `requestId`, and add a machine-readable `code` and `help`. The help object supplies `method`, `contentType`, a minimal JSON `example`, the same-route `endpoint`, the recommended v2 endpoint and the OpenAPI URL. Send only the example/input fields as the body, not the help object.

Correct the request and retry `help.endpoint` to preserve the response version. Only authorize payment after a valid HTTP 402 challenge and within the existing wallet spending policy. Wrong content types remain HTTP 400; form data is not silently converted.

GET/HEAD on `/verify` and `/v2/verify` return HTTP 405 with `Allow: POST`. GET includes JSON guidance; HEAD has no body. OPTIONS returns HTTP 200 with `Allow: POST`. Use `/healthz` or `/readyz` for health checks. These guidance responses do not perform verification or charge a payment.


## Opt-in settled-result recovery

Generate and save a cryptographically random 32-byte hexadecimal secret before POST, then send it in `SAVER-RECOVERY-TOKEN`. Retrieve through `GET https://api.saververify.com/results` with the same header. No wallet key, signature or new payment is required for retrieval. A completed response includes the original settlement receipt and `SAVER-RESULT-REPLAY: true`.

Retention is up to 24 hours. Check `resultRecovery.durable` in `/.well-known/x402` before depending on restart persistence. Pending/uncertain outcomes return 202 without evidence. A missing/expired record returns 404, which does not prove nonpayment. Never put the bearer token in URLs, public logs or source control, and never automatically create another payment after an ambiguous result.
